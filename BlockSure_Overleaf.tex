\begin{abstract}
Digital documents in distributed cloud networks are persistently vulnerable to silent corruption, malicious tampering, and unauthorized administrative overwrites. Conventional file integrity monitoring (FIM) systems rely on centralized Certificate Authorities or relational checksum catalogs, creating catastrophic single points of failure (SPoF) and insider repudiation risks. Conversely, naive on-chain storage scales linearly at 625,000 gas per kilobyte, rendering direct storage financially non-viable. Furthermore, existing decentralized solutions predominantly treat files as immutable, static artifacts, failing to integrate client-side privacy-preserving hashing, granular update authorization, and multi-version provenance into a single framework.

This paper presents \textbf{BlockSure}, a hybrid decentralized architecture that decouples content computation from cryptographic attestation. Using the browser-native W3C Web Crypto API, 256-bit SHA-256 fingerprints are calculated entirely within client RAM without transmitting raw bytes off-device. These fingerprints are registered into an Ethereum Virtual Machine (EVM) smart contract (\texttt{FileIntegrityRegistry.sol}) that records backward-linked provenance pointers (\texttt{previousHash}) and enforces on-chain Role-Based Access Control (RBAC). In our controlled empirical evaluation of 20 test files across 7 mutation categories, BlockSure demonstrated a 100.0\% tamper detection rate while strictly preserving the filename invariance property. Hardware-accelerated client hashing achieved sustained throughputs between 220 and 303~MB/s. On-chain benchmarking confirmed that read-only verification queries consume 0 transaction gas, while version updates consume 224,845 gas---a measured 36.5\% reduction relative to initial registration (354,375 gas). We provide an epistemic multi-tier comparative benchmark against centralized databases, naive on-chain storage, IPFS hybrids, and Merkle tree anchoring, demonstrating that BlockSure provides enterprise-grade integrity auditing with zero raw-file leakage.
\end{abstract}

\section{Introduction}
Digital assets such as legal contracts, medical archives, financial ledgers, and firmware binaries form the backbone of modern data-driven enterprises. Despite widespread adoption of Transport Layer Security (TLS) and disk-level encryption, files at rest remain highly susceptible to bit rot, ransomware injection, and malicious alteration by privileged system administrators.

Traditional File Integrity Monitoring (FIM) systems rely on local checksum catalogs (e.g., Tripwire, OSSEC) or cloud databases. These architectures suffer from three critical flaws:
\begin{enumerate}
    \item \textbf{Administrative Repudiation:} A compromised database administrator (DBA) or cloud provider can modify file contents and silently recalculate stored checksums without producing an immutable audit trace.
    \item \textbf{Single Point of Failure (SPoF):} Centralized validation endpoints are susceptible to distributed denial-of-service (DDoS) outages and network partitions.
    \item \textbf{Absence of Cryptographic Lineage:} When files undergo legitimate revisions, conventional systems overwrite prior hashes or maintain disconnected logs, obscuring historical lineage.
\end{enumerate}

To address these vulnerabilities, this research investigates four core Research Questions (RQs):
\begin{itemize}
    \item \textbf{RQ1 (Detection Efficacy):} Can client-side SHA-256 hashing coupled with on-chain anchoring reliably detect bit-level alterations across diverse file formats while maintaining filename invariance?
    \item \textbf{RQ2 (Authorization Enforcement):} Can smart-contract-level RBAC definitively prevent unauthorized parties from appending or overwriting versions without centralized servers?
    \item \textbf{RQ3 (Economic Feasibility):} What are the computational gas costs and latency overheads of maintaining append-only cryptographic version rings on the EVM?
    \item \textbf{RQ4 (Scalability):} How does client hashing scale across expanding file payloads, and can read verifications achieve zero network gas fees?
\end{itemize}

\subsection{Mathematical Formulations}
\textbf{Definition 1 (Cryptographic Digest):} Let $F \in \{0, 1\}^*$ be the arbitrary-length sequence of bytes comprising a digital document. The fingerprint $H(F)$ is computed client-side using NIST FIPS 180-4 SHA-256:
\begin{equation}
    H(F) = \text{SHA-256}(F) \in \{0, 1\}^{256} \equiv \texttt{bytes32}
\end{equation}
By the second-preimage resistance of SHA-256, it is computationally infeasible to find $F' \neq F$ such that $H(F') = H(F)$.

\textbf{Definition 2 (Provenance Version Linked-List):} A version record $\mathcal{V}_n$ for file identifier $ID$ is defined as the tuple:
\begin{equation}
    \mathcal{V}_n = \langle n, H(F_n), \text{name}, \text{size}, t_n, H_{\text{prev}}, u_n, \text{note} \rangle
\end{equation}
where $u_n$ is the updater address, and $H_{\text{prev}}$ forms the cryptographic backward link (illustrated in Fig.~\ref{fig:provenance_chain}):
\begin{equation}
    H_{\text{prev}} = \begin{cases} 
    0x0^{64}, & \text{if } n = 1 \text{ (Genesis Root)} \\ 
    H(F_{n-1}), & \text{if } n > 1 \text{ (Provenance Link)} 
    \end{cases}
\end{equation}

\textbf{Definition 3 (Two-Phase State Verification):} Given a client-computed hash $h_{\text{calc}} = H(F_{\text{local}})$:
\begin{equation}
    \mathcal{D}(ID, h_{\text{calc}}) = \begin{cases} 
    \text{VERIFIED}, & \text{if } h_{\text{calc}} = H(F_{\text{current}}) \quad [O(1)] \\
    \text{HISTORICAL}(k), & \text{if } \exists k < \text{cur} : h_{\text{calc}} = H(F_k) \quad [O(V)] \\
    \text{TAMPERED}, & \text{if } \forall k \le \text{cur} : h_{\text{calc}} \neq H(F_k) \quad [O(V)] \\
    \text{NOT\_REGISTERED}, & \text{if } ID \notin \mathcal{K}_{\text{registry}} \quad [O(1)]
    \end{cases}
\end{equation}

\subsection{Smart Contract Algorithms}
The core logic is implemented in Solidity (\texttt{FileIntegrityRegistry.sol}). Algorithms~\ref{alg:add_version} and \ref{alg:verify_hash} outline version updates and state verification.

\begin{algorithm}[h]
\caption{Authorized Version Registration (\texttt{addVersion})}
\label{alg:add_version}
\begin{algorithmic}[1]
\REQUIRE $ID \in \mathcal{K}_{\text{registry}}$
\REQUIRE $\text{caller} = \text{owner} \lor \text{caller} \in \mathcal{C}_{ID}$
\REQUIRE $h_{\text{new}} \neq 0 \land h_{\text{new}} \neq H(F_{\text{current}})$
\STATE $n \leftarrow \text{currentVersion} + 1$
\STATE $h_{\text{prev}} \leftarrow H(F_{\text{current}})$
\STATE $\text{currentVersion} \leftarrow n$
\STATE $\mathcal{V}_n \leftarrow \langle n, h_{\text{new}}, \text{name}, \text{size}, \text{timestamp}, h_{\text{prev}}, \text{caller}, \text{note} \rangle$
\STATE \textbf{emit} \texttt{VersionAdded}($ID, \text{caller}, n, h_{\text{new}}, h_{\text{prev}}, \text{timestamp}$)
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[h]
\caption{Two-Phase State Verification (\texttt{verifyHash})}
\label{alg:verify_hash}
\begin{algorithmic}[1]
\REQUIRE $ID \in \mathcal{K}_{\text{registry}}$
\STATE $n \leftarrow \text{currentVersion}$
\STATE $h_{\text{cur}} \leftarrow \mathcal{V}_n.\text{fileHash}$
\IF{$h_{\text{calc}} == h_{\text{cur}}$}
    \RETURN $(\text{true}, n, n, h_{\text{cur}}, \text{owner}, \mathcal{V}_n.t)$ \COMMENT{$O(1)$ Fast Path}
\ENDIF
\FOR{$v = 1$ \TO $n - 1$}
    \IF{$\mathcal{V}_v.\text{fileHash} == h_{\text{calc}}$}
        \RETURN $(\text{false}, v, n, h_{\text{cur}}, \text{owner}, \mathcal{V}_n.t)$ \COMMENT{$O(V)$ Traversal}
    \ENDIF
\ENDFOR
\RETURN $(\text{false}, 0, n, h_{\text{cur}}, \text{owner}, \mathcal{V}_n.t)$ \COMMENT{Tampered}
\end{algorithmic}
\end{algorithm}

\textbf{Arithmetic Gas Check:} Updating an existing file (\texttt{addVersion}) requires 224,845 gas, compared to 354,375 gas for initial registration:
\begin{equation}
    \Delta \text{Gas} = \frac{354,375 - 224,845}{354,375} \times 100 = \frac{129,530}{354,375} \times 100 = \mathbf{36.55\%}
\end{equation}
This 36.5\% efficiency gain occurs because storage slots for the parent record and index pointers are already allocated during registration. Furthermore, verification queries are read-only EVM \texttt{view} calls that consume \textbf{zero network transaction gas}.

\subsection{Experiment 4: Execution Latencies}
Latencies were benchmarked across 20 read queries and 5 on-chain write transactions under two configurations:
\begin{itemize}
    \item \textbf{In-Process EVM Execution:} Read latency $\mu = 2.36$~ms (min: 1.61~ms, max: 3.63~ms); Write confirmation $\mu = 3.59$~ms.
    \item \textbf{Localhost HTTP JSON-RPC:} Read latency $\mu = 19.84$~ms (min: 3.45~ms, max: 142.68~ms); Write confirmation $\mu = 53.46$~ms.
\end{itemize}
On public Ethereum networks, read queries are subject to standard JSON-RPC network transit (50--250~ms via Alchemy/Infura), while writes require consensus block slot intervals (12 seconds on Ethereum PoS).

\subsection{Critical Performance Insights}
\textbf{1. The $O(1)$ Gas Barrier vs. Client RAM:} Storing file data directly into EVM storage slots (\texttt{SSTORE}) costs 20,000 gas per 32 bytes ($\approx 625,000$ gas/KB). A 10~MB file would consume $6.25 \times 10^9$ gas, exceeding the 30M block gas limit by 208 times. BlockSure anchors only the 32-byte digest, making smart contract gas strictly $O(1)$ with respect to file size. Practical file size limits are determined by browser memory and V8 \texttt{ArrayBuffer} boundaries (~1--2~GB).

\textbf{2. Latency Parity:} IPFS hybrids suffer from multi-hop Distributed Hash Table (DHT) lookup delays (850--3,200~ms, Fig.~\ref{fig:latency_comparison}). BlockSure achieves sub-20~ms query latency on local RPC, achieving speed parity with centralized REST APIs while eliminating server-side trust.

\textbf{3. Justification of RBAC Overhead:} Initial registration in BlockSure consumes 354,375 gas compared to ~115,000 gas for basic CID notarization. This overhead establishes the on-chain dynamic collaborator mapping and provenance arrays. This investment pays off with a 36.5\% gas reduction on version updates and a 100.0\% rejection rate against unauthorized overwrite attempts.

\section{Threats to Validity and Limitations}
\begin{enumerate}
    \item \textbf{Off-Chain File Availability:} BlockSure attests to file integrity; it does not replicate physical data. If all off-chain copies are lost, the blockchain proves authenticity but cannot recover contents.
    \item \textbf{Private Key Security:} Compromise of an owner's private key allows malicious collaborator authorization. Multi-signature schemes (e.g., Safe) mitigate this threat.
    \item \textbf{Public Metadata Exposure:} While raw file contents remain private in client memory, metadata (filename, file size, timestamp) is visible on-chain.
    \item \textbf{Local vs. Public Network Latency:} While gas mechanics are identical on Ethereum Mainnet, transaction confirmation times on public networks are governed by 12-second PoS slot intervals.
\end{enumerate}

\section{Conclusion}
This paper presented \textbf{BlockSure}, a client-side privacy-preserving blockchain architecture that unifies SHA-256 fingerprinting, Role-Based Access Control, and append-only version provenance. By keeping raw files off-chain and anchoring 32-byte digests in a Solidity smart contract, BlockSure provides tamper detection with zero raw-file transmission. Empirical evaluation demonstrated 100.0\% tamper-detection accuracy across 20 controlled test files, zero network gas costs for verification queries, a 36.5\% gas reduction on version updates, and sub-20~ms query latency. Future work includes integrating decentralized pinning layers (IPFS/Filecoin) and zero-knowledge proofs (zk-SNARKs) for selective metadata redaction.
